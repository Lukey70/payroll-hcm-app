Payroll/HCM App v1.1.41 code review

- Added self-service.js service layer and standalone ESS/MSS UI adapter. Engine exports these for both browser and Node tests. Browser load order is DataStore, PaymentDetails, SelfService, PayrollEngine, App.
- Scope checks occur at each service action; ESS derives employee ID from the signed-in user, ignoring submitted target IDs. MSS derives current direct reports from Reports To and effective position occupants. Self-approval and inactive manager roles are rejected.
- Request validation uses a cloned validation state with pending requests temporarily treated as approved. Actual state/payroll remains unchanged until approval. Current/future pending reservations and later annual commitments are tested. Approval excludes its own request during revalidation.
- Denial requires a comment. Employee withdrawal is pending-only; manager deletion is approved-only and archived. Finalised leave deletion is tested for retro reversal with frozen original payslips.
- Alerts contain explicit recipient IDs and per-recipient read status. Initial manager submission alerts are excluded from the payroll bell; overdue reminders target manager and payroll. Current manager reassignment updates pending routing.
- MSS earnings save validated source dates/type/units/positions. Rate-based amounts retain an empty amount override so the payroll engine calculates real rate-based earnings; fixed/date allowances follow engine rules. Current/previous/next periods mirror payroll Additional Earnings.
- Read-only views construct scoped tables and expose no personal/bank/tax/super mutation controls. Full sensitive data still resides in localStorage; UI/service authorization is not a server-side security boundary.
- Reimbursement nonTaxable flag propagates into current/retro tax handling; presentation label changes do not alter source descriptions used for settlement. Frozen old withholding is not silently rewritten.
- Existing UI and regression tests pass alongside role/action/DOM-handler tests. A DOM harness dispatch bug was fixed in the harness while testing; no live browser QA is claimed.

Material limitations: browser-local shared-data model, existing browser-readable credentials, no server authentication/authorization, no closed-app notifications, no real employee data supplied. Production multi-user security remains a separate backend task, as documented.
